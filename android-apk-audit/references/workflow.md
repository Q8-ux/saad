# إجراءات التحليل والتعديل والتحقق

## 1. تحديد التسليم

سجّل اسم المشروع والملف ونوع الحزمة وبصمة SHA-256 والتعديل المطلوب. حدد هل
المطلوب تقرير، مشروع معدل من المصدر، APK مستقل، أم تجربة على جهاز اختبار.
إذا كان الإدخال AAB أو مجموعة split APK فحدد جميع الأجزاء؛ لا تعِد تسمية AAB
إلى APK ولا تفترض أن base.apk وحده يكفي. لا ترفع التطبيق لخدمة خارجية لمجرد التحليل.

## 2. فحص ثابت قبل التعديل

شغّل doctor ثم inspect_apk. فحص البنية لا ينفذ التطبيق ولا يستخرج موارده.
اختر بيئة معزولة لفك الملفات غير الموثوقة. افحص Manifest المفكوك والصلاحيات
ومكونات exported وإعدادات الشبكة والأسرار المكشوفة عند توفر أداة تفكيك.
لا تطبع الأسرار في التقرير؛ اذكر نوعها وموقعها بعد التنقيح. لا تصنف وجود
صلاحية أو اسم مكتبة بحد ذاته كثغرة أو كدليل برمجيات خبيثة.

أمثلة موثقة في المصادر، تنفذ فقط بعد فحص أدواتها ومسارات الإدخال والإخراج:

```bash
droidasc getmanifest app.apk -o AndroidManifest.xml
droidasc findrefs app.apk string SEARCH_TERM -o references.txt
jadx -d decompiled app.apk
apktool d app.apk -o decoded
apktool b decoded -o control-unsigned.apk
```

هذه الأمثلة لا تعني أنها نُفذت في البيئة الحالية. لا تضف `-f` لحذف مخرجات
سابقة تلقائياً، ولا تقبل APK يحتوي مسارات استخراج خطرة أو تكرار أسماء الأعضاء.
تحقق من `--help` للإصدار المثبت قبل الاعتماد على خيارات إصدار آخر.

## 3. اختيار موضع التعديل

إن توفر الكود ومشروع البناء فعدّل المصدر واستخدم اختبارات المشروع. إن لم
يتوفر إلا APK فحدد نوع التطبيق: Java/Kotlin أو Flutter أو React Native أو
Unity أو كود native. أسماء الملفات قرائن تحتاج إثباتاً، وليست تصنيفاً قطعياً.
حدد هل الإعلان في SDK محلي أو WebView أو إعداد بعيد أو محتوى من الخادم.
اختبر التغيير المطلوب ضمن نطاقه؛ حذف callbacks عشوائياً قد يعلق التدفق.

احتفظ بنسخة أصلية ونسخة control مبنية دون تعديلات. اختبر control أولاً، ثم
غيّر نقطة واحدة وقارن الملفات والتعليمات والوظائف. تجنب أي تعديلات خارج الطلب.
إذا كان القرار مفروضاً على الخادم فوثّق هذا الحد وعدّل backend المملوك إن كان
ضمن المهمة؛ تعديل العميل وحده لا يغيّر صلاحيات الخادم.

## 4. البناء والتوقيع

استخدم مجلد إخراج منفصلاً وسجّل كل مرحلة: rebuild ثم alignment ثم signing ثم
verification. استخدم أدوات Android SDK الرسمية أو uber-apk-signer وفق وثائقها
وبمفتاح يحدده سياق المشروع. لا ترسل كلمة مرور المفتاح في arguments أو logs.
لا تكتب keystore أو APK أو سجلات المستخدمين داخل المستودع العام.

تغيير الشهادة قد يمنع التحديث فوق نسخة سابقة أو يعطّل خدمات مرتبطة بالتوقيع.
لا تحل تعارض التوقيع بحذف التطبيق تلقائياً؛ الحذف قد يفقد بياناته. لا تستخدم
تعطيل فحوص الحماية كإصلاح افتراضي. اطلب التوضيح فقط إذا بقي قرار فعلي غير
مصرح به مثل تغيير هوية التوقيع أو حذف بيانات حية.

## 5. التشغيل والتقرير

استخدم جهاز اختبار مناسباً وإصدارات متوافقة من ADB وFrida. لا تفترض أن وجود
Frida يعني وجود frida-server مناسب أو root أو صلاحية الربط. ابدأ بالفحص
الثابت واستخدم التحليل الديناميكي إذا احتاجه السؤال.

تحقق حسب ميزات التطبيق من التثبيت والإقلاع والتنقل والدخول والشبكة والصوت
والميكروفون والدفع والتحديث. في المشاريع العربية اختبر RTL والخطوط وتصدير
PDF والصور عند وجودها. سجّل الاختبارات غير المنفذة كغير منفذة، ولا تعلن
جاهزية إصدار للنشر اعتماداً على نجاح البناء وحده.

صيغة التقرير: النتيجة المثبتة، الأدلة، الملفات المعدلة، الاختبارات المنفذة،
المخاطر المتبقية، والخطوة التالية. افصل مستوى «فحص بنية الحزمة» عن «تحليل الكود»
و«تم البناء» و«تم التوقيع» و«تم الاختبار على الجهاز».
