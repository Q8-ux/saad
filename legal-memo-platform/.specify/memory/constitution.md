# دستور سابق — هندسة المواصفات والتنفيذ

## Core Principles

### I. الدقة القانونية وقابلية التتبع

MUST فصل الوقائع المدخلة، النص التشريعي، المبدأ القضائي، وتطبيقه على الحالة. MUST عدم اختلاق مادة أو قانون أو رقم طعن أو منطوق أو مستند. MUST إرجاع حالة نقص/مراجعة عند غياب الدليل. مخرجات الوكيل مسودة؛ الاعتماد القانوني النهائي يبقى للمختص.

### II. حدود مصادر التشريعات والأحكام

MUST الحفاظ على البحث داخل ملف التشريعات المربوط وقاعدته المشتقة وفق `../sabeq-legal/integrations/legislation-laws-path/README.md`، دون بحث خارجي احتياطي لهذا المسار. MUST حفظ معرفات المصدر والصفحات داخلياً للتحقق وإعادة قراءة النص من الخادم قبل الاستشهاد. لا يُنقل سجل المصادر الداخلي إلى المذكرة خلافاً للقالب المعتمد. MUST عدم تحويل ذكر محكمة أو حاشية إلى حكم تمييز مستقل؛ غياب الحكم المراجع يُسجّل كغياب.

### III. خصوصية ملفات العملاء

MUST معالجة الملفات والبيانات الشخصية في الخلفية الآمنة، وعدم حفظها في GitHub أو Pages أو المواصفات أو لقطات الاختبار أو سجلات القياس والأخطاء. MUST استخدام بيانات اصطناعية واضحة في الاختبارات وعدم نشر قواعد القضايا أو مفاتيح الخدمة. مصادر صفحات عامة لا تعني تفويض إرسال وقائع عميل إلى بحث خارجي.

### IV. توافق السلوك والهوية

MUST الحفاظ على السلوك المعتمد حالياً للتسجيل والضيف والرفع والتوليد والدفع والتصدير إلا بطلب صريح. لا تُعاد قيود أو حقول قديمة من وثيقة أقدم عند تعارضها مع طلب أحدث. MUST الحفاظ على الشعار الرسمي وخط المهند المتاح فعلياً والعربية/الأردية RTL والإنجليزية LTR والقراءة على الجوال. تغييرات القوالب القانونية تحترم المحاذاة وحافظة المستندات المعتمدة.

### V. مواصفات محدودة وأدلة قبول

MUST تحديد المطلوب والنطاق والافتراضات ومعايير قبول قابلة للاختبار قبل تغيير مؤثر. MUST ربط `tasks.md` بالمتطلبات وتوثيق حالات الفشل: غياب المصدر، فشل الرفع أو الاتصال، انتهاء المهلة والإلغاء. SHOULD إعادة استخدام المواصفات والكود والاختبارات القائمة؛ التعديل البسيط لا يحتاج دورة كاملة.

### VI. حدود المستودع والنشر

MUST قصر هذا المسار على خلفية سابق وواجهته وتعليمات تطويرهما. MUST عدم تعديل مشاريع المستودع الأخرى أو استبدال إعداداتها. MUST فصل نجاح أدوات التطوير عن نجاح واجهة منشورة. ادعاء تحسن السرعة أو الجودة يحتاج قياساً ملائماً؛ تثبيت Spec Kit وحده لا يغيّر محرك الصياغة أو يضيف حكماً قضائياً.

## Development and quality gates

- اقرأ المواصفة والخطة والمهام قبل التنفيذ، وحل الغموض الذي يغير النتيجة.
- شغّل الاختبارات ذات الصلة بالحد الفعلي المتأثر. تحقق من الواجهة والتصدير فعلياً عندما يتغيران؛ لا تستبدل ذلك بفحص وجود ملفات.
- احتفظ بالتغييرات في نطاق صغير قابل للرجوع. لا تفقد أخطاء التحقق أو صلاحيات المستخدم أثناء إعادة الهيكلة.
- لا تُسجل موافقة مراجع أو اختباراً حياً أو نشرًا ناجحاً دون دليل. لا يحل تقييم AI للمواصفات محل التحقق القانوني المختص.
- راجع اختلافات النسخة المثبتة قبل تحديثها؛ لا تشغّل إضافات المجتمع أو hooks غير المراجعة تلقائياً.

## Governance

هذه القواعد تترجم متطلبات سابق الحالية، وليست شهادة بأن كل وظيفة في الإنتاج تستوفيها. تعليمات المستخدم الأحدث تتقدم على الملاحظات القديمة، وتُحدّث المواصفات عند تغير الطلب. تجري مراجعة الدستور عند تغير قواعد المشروع، لا عند كل تشغيل.
