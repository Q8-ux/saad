# تفعيل التحقق والدفع في سابق القانونية

هذا التغيير ينفذ الحساب الموثق، حفظ طلب المذكرة ومرفقاته، الدفع لدى مزود خارجي، وتوليد المذكرة بعد تأكيد الدفع من الخادم. يحتاج تشغيله الفعلي إلى بيانات المزود والسعر وقاعدة البيانات. وجود حقول إعداد مكتملة لا يثبت صلاحية المفاتيح أو وصول الرسائل.

## ما يلزم من صاحب الموقع

| المطلوب | الاستخدام |
| --- | --- |
| اسم البنك واسم بوابة التجارة الإلكترونية وتوثيق API | تحديد طريقة إنشاء جلسة الدفع ومراجعة حالتها؛ المفتاح وحده لا يحدد البروتوكول |
| مفاتيح الاختبار والإنتاج وبيانات التاجر المطلوبة من المزود | تحفظ على الخادم أو في شاشة الإدارة المشفرة |
| سر توقيع Webhook وإعداد إشعارات الدفع لدى المزود | تأكيد الدفع حتى إذا أغلق العميل الصفحة |
| سعر المذكرة بالدينار الكويتي | يخزن بالفلس؛ 1.500 دينار = 1500 فلس؛ لا يوجد سعر تجاري مفترض |
| قناة التحقق المختارة وحساب إرسال مفعل | البريد عبر Resend، والرسائل النصية/واتساب عبر Twilio Verify في الربط الحالي |
| قاعدة PostgreSQL دائمة مع نسخ احتياطي | حفظ الحسابات والطلبات والمرفقات والمدفوعات بعد إعادة نشر الخدمة |
| بريد الإدارة | يدخل قائمة SABEQ_ADMIN_EMAILS للوصول إلى الإدارة بعد التحقق |

لا ترسل المفاتيح في المستودع أو المحادثات. تدخل عبر إعدادات الخادم أو صفحة billing-admin.html بعد نشرها عبر HTTPS. الصفحة لا تعرض المفاتيح المحفوظة، والحقل الفارغ يحتفظ بالقيمة الحالية.

## نطاق الربط الحالي

- لم يُفترض أن مفتاح البنك تابع لمزود معين. المتاح حالياً محول اختياري لـ **MyFatoorah الكويت**، لا يعمل إلا عند اختياره صراحة وتزويده ببيانات حساب مطابق. إذا كانت بوابة البنك مختلفة، يلزم محولها وفق توثيقها وتحديث قائمة نطاقات صفحة الدفع في الخادم والواجهة.
- يستخدم MyFatoorah SendPayment مع LNK لإنشاء رابط خاص بالطلب، وGetPaymentStatus للتحقق من الفاتورة والقيمة والمرجع والعملة وحالة التحصيل. العودة إلى الموقع لا تثبت الدفع.
- يستقبل Webhook V2 PAYMENT_STATUS_CHANGED بتوقيع MyFatoorah-Signature ثم يعيد الاستعلام من API. لا يدعم إشعارات V1 في هذا التنفيذ.
- البريد يستخدم Resend ومُرسلاً موثقاً على نطاق الموقع. SMS وWhatsApp يستخدمان خدمة Twilio Verify المفعلة للقناة والبلد؛ لا يفترض الكود توفر القنوات في حساب المزود.
- التحقق يثبت ملكية قناة التواصل فقط. البريد والهاتف حسابان مستقلان ما لم تُضف عملية ربط موثقة لاحقاً؛ ينبغي للعميل العودة باستخدام القناة نفسها لرؤية طلباته.
- شاشة الاسترداد تسجل الطلب ومتابعته ومرجع إرساله للبنك. **لا تنفذ استرداداً مالياً ولا تؤكد وصول الأموال للعميل**؛ الربط الآلي للاسترداد يحتاج توثيق بوابة البنك واعتماد سياسة الاسترداد.

## إعداد الخدمة الحالية

الخادم موجود في Q8-ux/saad تحت legal-memo-platform، ويبدأ بواسطة npm start (gateway.js). الواجهة الفعلية في Q8-ux/sabeq-legal-system، والنسخة المقابلة في sabeq-legal داخل المستودع العام. يجب تنسيق نشرهما.

1. احتفظ بمتغيرات الخدمة الحالية، ومنها OPENAI_API_KEY وSESSION_SECRET. لا تنشئ خدمة Render بديلة أو تغير الخطة المالية تلقائياً.
2. أضف SABEQ_DATABASE_URL لقاعدة PostgreSQL دائمة. ينشئ التطبيق جداول commerce_* دون نقل أو حذف جداول القضايا القديمة. يلزم وصول CREATE TABLE في المخطط المخصص. الاتصال المشفر يجب أن يتحقق من شهادة الخادم.
3. شغّل node scripts/create-commerce-secrets.js محلياً مرة واحدة. ينشئ ملفاً محلياً مستثنى من git دون طباعة الأسرار. انقل القيمتين إلى إعدادات الخدمة بأمان، واحفظ نسخة احتياطية منفصلة لمفتاح التشفير. تغيير SABEQ_ENCRYPTION_KEY عشوائياً يجعل البيانات القديمة غير قابلة للقراءة.
4. اضبط SABEQ_ADMIN_EMAILS وSABEQ_PUBLIC_URL. يمكن استخدام SABEQ_ADMIN_BOOTSTRAP_SECRET للدخول الأول إلى billing-admin.html. بعد اختبار دخول الإدارة بالبريد، احذف سر الدخول الأول من إعدادات الخدمة وأعد نشرها؛ تنتهي جلسات الإدارة خلال 30 دقيقة.
5. أضف قناة تحقق واحدة على الأقل. للبريد: SABEQ_RESEND_KEY وSABEQ_EMAIL_FROM بصيغة بريد فقط، ثم SABEQ_VERIFICATION_CHANNELS=email. للهاتف: TWILIO_ACCOUNT_SID وAUTH_TOKEN وVERIFY_SERVICE بالأسماء الكاملة في .env.example، ثم sms أو whatsapp أو قائمة مفصولة بفواصل.
6. حدد السعر بالفلس. اترك بوابة الدفع غير مختارة حتى يتأكد تطابق حساب البنك مع الربط. إعدادات لوحة الإدارة المشفرة تتقدم على متغيرات البيئة؛ اجعل مصدر التعديل واضحاً للفريق.
7. في حساب MyFatoorah المطابق فقط، أضف المفتاح وسر Webhook، واختر test. سجل عنوان API الحالي مع المسار /api/payments/webhook واستعمل Webhook V2 لإشعار الدفع. لا تستخدم رابط الواجهة كعنوان Webhook. رابط العودة ينشئه الخادم من SABEQ_PUBLIC_URL ومعرف الطلب.
8. نفذ اختباراً فعلياً في بيئة المزود: وصول OTP، فشل الرمز، انقضاؤه، نجاح الدفع، إلغاؤه، تكرار إشعاره، وإغلاق المتصفح قبل العودة. في الإنتاج، الدفع التجريبي متاح للإدارة وحدها.
9. بعد نجاح الاختبارات، أدخل مفاتيح الإنتاج المطابقة واختر live، ثم انشر الواجهة والخادم بالتنسيق. لا تدمج الحاجز الإلزامي على الموقع الحالي قبل توفير قاعدة البيانات وخدمة الإرسال؛ هذا سيوقف توليد المذكرات عمداً حتى اكتمال الإعداد.

## السلوك والتحقق

المستخدم يملأ بيانات القضية، يؤكد حسابه، ويراجع المبلغ قبل الانتقال لصفحة الدفع المستضافة. يحفظ الخادم نسخة الطلب والمرفقات المختارة قبل الدفع، ويأخذ السعر من إعداداته. لا يستقبل الموقع بيانات البطاقة.

تكرار الطلب بالمفتاح نفسه يعيد الطلب ذاته. تكرار إنشاء الدفع يعيد الفاتورة المفتوحة نفسها؛ إذا انقطع الرد بعد إرسال طلب إنشاء الفاتورة، تبقى العملية قيد المراجعة ويستعلم الخادم عن مرجعها دون إنشاء فاتورة ثانية تلقائياً. لا تتغير تفاصيل الطلب المدفوع. تأكيد التحصيل يضع التوليد في طابور محفوظ بقاعدة البيانات.

فشل التوليد يحتفظ بالدفع، ويسمح بثلاث محاولات إجمالاً ثم تدخل الإدارة. النتيجة تحفظ مشفرة وتبقى متاحة في «طلباتي». انقطاع العامل أثناء التوليد يتحول بعد عشر دقائق إلى محاولة متوقفة قابلة للمراجعة/الإعادة؛ قد تتكرر تكلفة مزود الذكاء الاصطناعي إذا انقطع الخادم بعد إنتاج النص وقبل حفظه، دون تحصيل دفعة أخرى من العميل.

الرمز ستة أرقام، صالح لخمس دقائق ولمرة واحدة، مع انتظار دقيقة بين الإرسالات وحدود للمحاولات. الجلسات في ذاكرة تبويب المتصفح sessionStorage، وتبطل عند تسجيل الخروج. يعتمد الخادم على هوية موثقة ولا يقبل رمز الضيف القديم. الخدمات التي تستهلك الذكاء الاصطناعي تتطلب حساباً موثقاً وتخضع لحد استخدام.

المرفقات تحفظ مشفرة في PostgreSQL: حتى 25 ملفاً و50 ميجابايت للدفعة، و200 ميجابايت للحساب. المرفقات غير المرتبطة بطلب تنظف بعد سبعة أيام. حدود الحفظ والسياسة طويلة المدى تحتاج اتفاقاً قبل الإطلاق؛ لا يوجد ترحيل تلقائي لملفات الضيوف القديمة أو ربطها بهويات جديدة.

## الاختبارات

```sh
cd legal-memo-platform
npm ci
npm test
```

اختبارات commerce تستخدم مزودي إرسال ودفع وتوليد محاكيين؛ لا ترسل رسائل ولا تخصم أموالاً. تشمل الملكية، التشفير، OTP، قفل المحاولات، تكرار الفاتورة، صحة المبلغ والعملة، التوقيع، حفظ النتيجة، إعادة المحاولة، وعزل المرفقات.

اختبارات commerce-ui تفحص شاشة التحقق ومراجعة المبلغ وإعادة فتح النتيجة بواسطة jsdom. هي اختبارات لمنطق DOM ولا تحل محل فحص التصميم بصرياً في متصفح الجوال؛ تعذر فتح المعاينة المحلية في متصفح المراجعة لهذه الجلسة.

يشغل GitHub Actions المجموعة نفسها على PostgreSQL 16. لتكرارها محلياً، عيّن TEST_DATABASE_URL لقاعدة **اختبار** تسمح بإنشاء وحذف مخططات؛ الاختبارات تنشئ مخططاً عشوائياً لكل حالة وتحذفه بعد انتهائها. لا تستخدم قاعدة الإنتاج.

تشغيل الخادم في production أو Render يرفض SQLite لحفظ المدفوعات. الواجهة تعرض رسالة إعداد واضحة بدلاً من نجاح وهمي عند غياب الخدمات.

المراجع: [MyFatoorah SendPayment](https://docs.myfatoorah.com/docs/send-payment)، [Payment status](https://docs.myfatoorah.com/docs/get-payment-status)، [Webhook signature](https://docs.myfatoorah.com/docs/webhook-signature)، [Twilio Verify](https://www.twilio.com/docs/verify/api)، [Resend](https://resend.com/docs/api-reference/emails/send-email).
